# 给套件加一个新控件

> 第三版（2026-10-12）。初稿用开关试过一次（四个库）；第二版是做后台页面框架时，五个新控件 × 五个组件库照它做完以后改的；第三版是做客户列表时，七个新控件（表格、分页、标签、日期范围、对话框、单选、多行输入）× 五个组件库照它做完以后改的，卡住和含糊的地方都改进来了。
> 写给 AI 照着执行，设计师也看得懂。每一步都写了：做什么、改哪个文件、怎么算做完。代码细节交给 AI，判断交给人。

比如你要给套件加一个「开关」「对话框」「表格」。做完以后：页面里写一次 `<kit.Switch>`，所有登记过的组件库都能用，而且自动检查证明它们长得一样、用起来一样。

**检查工具不认识任何组件库、任何控件**，加新控件不用为它改检查工具。但新控件可能带来新的交互方式（比如鼠标悬停才弹出的子菜单、↑ ↓ 键），检查项不够用时可以给检查工具加一种通用的做法——**只能是对所有组件库、所有控件都成立的通用规则**，不能为某个组件库开特例。

---

## 先认识四样东西

| 名字 | 是什么 | 在哪 |
|---|---|---|
| **控件规格** | 这个控件统一成什么样：多大、什么颜色、悬停和禁用时怎么变。从规范（Design.md）的取值算出来，不写死颜色 | `spec/src/controls.ts` |
| **套件接口** | 页面怎么用这个控件：有哪些属性（比如 `checked`、`disabled`） | `react/src/kit/types.ts`、`vue/src/kit/types.ts` |
| **套件** | 每个组件库一份，把「一个开关」翻译成这个组件库的真组件，再对齐到控件规格 | `react/src/kits/*`、`vue/src/kits/*` |
| **部件地图** | 告诉检查工具：用户看得见的那个框，在这个组件库里是哪个元素 | 每个套件里的 `parts`；部件名在 `spec/src/parts.ts` |
| **数据形状** | 控件要的数据（菜单项、面包屑项、下拉菜单项）长什么样，React 和 Vue 共用 | `spec/src/items.ts` |

还有一个「场景」：检查页和演示页上摆出来的东西。表单类的控件先放进**控件样张**（`examples/src/scenes/controls/`）核对；只在页面里才有意义的控件（导航菜单、面包屑）放进它所在的页面场景（`examples/src/scenes/admin/`）。

```bash
npm run check
```

全部通过再开始。没通过就先修，不然分不清哪些问题是新控件带来的。新的 worktree 先 `npm ci`。完整检查要跑 7–10 分钟，可以放在后台跑，同时开始第 1 步。

## 第 1 步：写控件规格（设计决定，要人来定）

**改哪里**：`spec/src/controls.ts`

1. 在 `ControlSpec` 里加一组，比如 `switch: { width, height, ... }`，每一项写一句注释说它是什么。
2. 在 `resolveControls` 里给出取值：
   - 颜色一律从规范的角色取（`t['action.primary']`、`t['border.control']`……），不写 `#xxxxxx`；
   - 尺寸可以写固定数字（像复选框的 16px），也可以从角色推算（像标签栏高度取 `size.controlLarge`）；
   - 只写**用户看得见的**：大小、颜色、圆角、留白，以及悬停、按下、禁用、聚焦时的变化。
3. 第一版怎么定：先看设计稿；没有设计稿就参考一个现有项目（比如你们已经在用的后台）里这个控件的样子，取一个大多数组件库接近的值。**写清楚这是第一版**，设计师在演示页里看过再调。
4. **写成看得见的数，并写清楚「相对谁」**：弹层离哪条边多远（「左边离侧栏右边缘 4px」而不是「离菜单项 4px」）、图标离哪条边多远、子项的文字和谁对齐。只写「间距 4」，五个组件库会量出五种「间距」。
5. **页面布局的尺寸不写进控件规格**：侧栏多宽、顶栏多高归页面布局（`core/styles`），控件只管自己（菜单填满侧栏）。
6. **交互也是规格**：每个状态归谁管（业务状态由页面传进来，像「选中哪一项」「哪些子菜单展开」；纯展示的状态归组件库，像「鼠标悬停时弹层开没开」）；键盘怎么操作（哪些元素在 Tab 顺序里、角色是什么、回车 / 空格 / 方向键 / Esc 做什么）。这些写进第 2 步接口的注释——不写，五个组件库就有五种键盘行为（导航菜单：antd 整个菜单一个 Tab 停靠点、方向键移动；Arco 每一项都能 Tab；TDesign 根本不能用键盘）。

**做完的标志**：`npm run typecheck` 通过。

**截图看一眼**：有的问题检查量不到，截图才看得出来——聚焦外圈被外层的 `overflow: hidden` 裁掉、页面样式依赖的 `aria-expanded` 没有、悬停时多出来的提示。检查页加 `&mode=native` 是组件库原生，写适配记录要的「原生实测数字」也从这里量。CSS 变量会自动生成，名字是 `--mh-c-<组>-<项>`（比如 `switch.thumbSize` → `--mh-c-switch-thumb-size`），套件里直接读。

> 尺寸有两档：默认（后台页面）和大号（登录这类关键表单）。新控件如果两档长得不一样，在规格里分开写；只有一档就不用分。

## 第 2 步：定接口（页面怎么用它）

**改哪里**：`react/src/kit/types.ts`、`vue/src/kit/types.ts`、`spec/src/adaptation.ts`

1. React：加一个 `XxxProps`，再在 `Kit` 里加 `Xxx: ComponentType<XxxProps>`。
2. Vue：在 `VueKit` 里加 `Xxx: Component`，注释里写清楚属性和事件，和 React 一一对应（React 的 `checked` + `onChange` 对应 Vue 的 `v-model`）。
3. `spec/src/adaptation.ts`：`AdaptedControl` 加上控件名，`CONTROL_NAMES` 写中英文名字（适配记录要用）。

**原则**：
- 接口只放页面**真正要用**的属性。以后要了再加，比一开始堆满强。
- 属性用业务的话（`checked`、`disabled`、`loading`），不用某个组件库的名字。
- 业务状态（开还是关）由页面传进来，控件自己不存。
- 控件要的数据（菜单项、面包屑项）的形状写进 `spec/src/items.ts`，React、Vue 共用。
- Vue 的事件：页面要双向绑定的用 `update:xxx`（`v-model:selected`），一次性的动作用普通事件名（`navigate`、`select`）。
- 键盘和读屏的要求写进接口注释（见第 1 步第 6 条），它和尺寸、颜色一样是规格。

**做完的标志**：`npm run typecheck` 会报错，说每个套件都缺这个控件——**这是对的**，第 4 步补上。

---

## 第 3 步：告诉检查工具要量哪些部件

**改哪里**：`spec/src/parts.ts`

1. `PartName` 加上部件名。部件 = 用户看得见的一块，比如开关有「轨道」和「圆点」两块，就加两个：`switch`、`switchThumb`。
2. `PART_NAMES` 写一句它是什么。

检查工具会在每个组件库里找这些部件，逐个量：位置、大小、底色、边线、圆角、不透明度。

- 部件选「有底色、有圆角的那个框」；最好它也就是**键盘聚焦的那个元素**（role 落在它上面）。这样聚焦外圈、悬停底色、Tab 顺序都量同一个元素，各组件库没法各量各的。
- 同一种东西在两个地方出现（侧栏里的菜单项、收起后弹层里的菜单项），可以用同一个部件名，检查工具按区域、按弹层分开量。

**做完的标志**：typecheck 报每个套件的 `parts` 缺了这几项——第 4 步一起补。

## 第 4 步：每个组件库各实现一遍

**改哪里**：每个套件一个文件，`react/src/kits/<库>/index.tsx`、`vue/src/kits/<库>/index.ts`，有的还有 `styles.css`。

每个组件库按这个顺序做：

### 先写一个参照实现，再几个库同时做

新控件不止一个、组件库有五个时，先在**源码在自己手里的那个库**（shadcn）照控件规格写一个参照实现，在演示页里量一遍，确认量出来就是规格里的数。**参照实现只拿自己跑检查，「全过」不说明什么**（一个值没有东西可比）；至少和另一个库比一次，才知道检查项本身量得对不对（文字提示那次就是这样漏的：shadcn 的提示移开鼠标不关，单独跑看不出来）。然后每个组件库一个 worktree、一个人（或 AI 会话），只改自己套件的文件，用 `npm run audit:kits -- --scene=<场景> --kits=shadcn,<这个库>` 一对一地对齐。最后合在一起跑完整检查。几个库互不相干，可以同时做；共用的文件（规格、接口、场景、检查工具）只由一个人改，别人发现要改就报告。

还没轮到的组件库先放一个占位：`pendingControl('Table')` 和部件 `PENDING_PART`（`react/src/kit/pending.tsx`、`vue/src/kit/pending.ts`），类型检查能过、页面能打开；做完以后不应该还有人用它（`grep pendingControl` 应该只剩这两个文件）。

组件库**没有这个控件**的（shadcn 没有「侧栏收起后悬停弹出的子菜单」，也没有「标在右上角的数字徽标」），用它的基础件拼（Radix 的 Popover、Badge 加定位），在适配记录里写清楚。shadcn 没有「表格组件」：照官方的数据表格示例，用 shadcn 的表格元素（Table、TableRow……）加 TanStack Table 拼。

**参照实现自己也可能错**：检查只证明「和参照一样」。如果你照规格做、和参照不一样，先对照规格判断谁错了：参照错了，把证据（报告里的哪一项、两边各是多少、规格写的是多少）报告给负责共用文件的人，自己按规格做。例：表头排序图标的「排了序变深色」，参照实现（shadcn、antd）因为共用的 `Icon` 丢了 `data-*` 属性一直没生效，「两边一致」其实是两边都错——是后面三个库照规格做时发现的。

**页面让做的「只做到哪」**：比如表格只做列、勾选、排序、状态标签、操作列、分页、空状态、加载中；**不做**固定列、虚拟滚动、展开行、拖拽、树形表格。要这些，就照这份说明把它当一个新控件（或给表格接口加一个属性）走一遍：先写规格（固定列的阴影、展开行的箭头……），再一个库一个库对齐。

### 4.1 先接上，不对齐

用这个组件库自己的组件，把接口的属性对上（开 / 关、禁用、点击后通知页面）。**接上以后提交一次**，再跑第一次检查、记下差多少——这是「对齐前」的真实数字，以后讲课、估工期都要用。

### 4.2 在部件地图里写清楚部件在哪

在套件的 `parts` 里写每个部件的选择器。怎么找：打开演示页（`npm run dev`），在浏览器里检查元素，找到**用户看得见的那个框**（有底色、有边线的那个），不是外面包着的、也不是里面隐藏的 `input`。

- 组件库用伪元素画的（比如 `::after`），写成 `{ selector: '…', pseudo: '::after' }`。例：antd 开关的圆点，白底和阴影画在 `.ant-switch-handle` 的 `::before` 上；
- 有的组件库把「能聚焦、读屏读得到」的元素和「看得见」的元素分开：Element 开关的 `role=switch` 在一个隐藏的原生 `input` 上，看得见的轨道是旁边的 `.el-switch__core`。部件地图写**看得见的**那个；检查里要聚焦、按键的目标用角色写（`[role=switch]`），检查工具会把隐藏的原生 `input` 算进来；
- 选择器写组件库自己的类名就行，它只给检查工具用，不影响组件。

### 4.3 对齐到控件规格

所有取值都读第 1 步的 `--mh-c-*` 变量（或者 `resolveControls(tokens)` 算出来的数值），不写死。

**手段从省事的先试**，前一种够不着才用后一种：

| 手段 | 例子 |
|---|---|
| 全局主题变量 | antd 的 `token`、Element 的 `--el-*` 变量 |
| 组件主题变量 | antd 的 `components.Switch`、Element 组件上声明的变量 |
| 组件属性 | Arco 输入框的 `height`、Element 下拉的 `offset` |
| 换类名 | shadcn 的源码在我们手里，直接换 Tailwind 类名 |
| 样式覆盖 | 组件库没留接口，在套件的 `styles.css` 里逐项改，**只在 `--aligned` 下生效**，不用 `!important` |
| 补交互 | 组件库的键盘、显隐行为不一样，套件补上或改写 |

**判断要不要统一**：问三个问题——这处不同会不会影响**业务状态**？会不会影响**用户看到的结果**？会不会影响**操作结果**？三个都不会，就保留组件库原来的做法，不用改。

**设计层的分歧交给人定**：几个组件库做法各有道理、问完三个问题还是要人判断的（比如表格排序是「整格能点」还是「表头里一个按钮」，对话框点遮罩关不关），**不能自己悄悄定**。在 `docs/取舍记录.md` 记一条：现象、各库怎么做、选项、推荐，标「待人决定」；可以先按推荐做、不阻塞，做完时一起交给人。判断顺序：用户能不能用（无障碍、键盘）> 设计一致 > 哪个库补起来省事。

原生模式（规范为 null）不做任何对齐，保留组件库自己的样子；「只设主题」模式只做第一种手段。

**React 套件里的 Hook 无条件调用**：`useContext`、`useState`、`useIconSet` 这些写在组件开头，不要写成 `aligned && swapsIcons(useIconSet())`——演示页切换外观时 `aligned` 会变，Hook 的调用顺序跟着变，React 会报错。

**受控的复合控件**：组件库常把展开状态自己存一份（Element 的菜单只在第一次读 `default-openeds`），要让它跟着页面传进来的值走；纯展示的状态（悬停弹层开没开）留给组件库，不要因为它去通知页面。组件库还会**自己发事件**：Element 的菜单挂载时自己发「展开」（连没有子菜单的一级项也发），antd 在叶子上按回车会把叶子记成「展开」，TDesign 收起后悬停也报「展开」。套件只把**用户的意图**（点击、键盘触发的）告诉页面，其余的拦下来，再把组件库拉回页面给的状态。

**哪些三档都要做、哪些只在对齐时做**：
- **接口约定，三档都成立**（这是「接上」）：业务状态受控、拦住组件库自己发的事件、弹层挂进作用域、选中以后通知页面、链接不真的跳转页面。原生那一档也是同一个页面，不能因为换了外观就把页面状态改乱。
- **只在对齐时做**（这是「对齐」）：样子，加上补交互里的角色、tabindex、回车空格、方向键、焦点去哪、`aria-*`。「组件库原生」那一档要如实展示组件库自己的样子和缺口（Element、TDesign 的菜单 Tab 进不去），对比的意义就在这里。
- **页面给的名字**（接口里的 `selectLabel`、`labels`、`closeLabel`、`pageLabel` 这类）是接口约定，**三档都补**：组件库有属性能传的用属性，没留地方的就渲染后改 DOM（`docs/取舍记录.md` 第 14c 条）。角色、`aria-expanded`、`aria-current` 这类是补交互，只在对齐档。
- **对齐档换了结构**（比如排序改成套件自己的按钮）时，部件地图的选择器把两档都写上（`:is(.mh-table-sort, .ant-table-column-sorters)`）：检查只量对齐档，量原生实测数字时也要找得到。

**弹层挂进作用域**：组件库没有「挂在哪」的属性时，看它是怎么找挂载容器的。Element 的 ElSubMenu 没有 `append-to`，但它按 ID 找容器（`#el-popper-container-<前缀>`），换一个前缀、在套件的挂载点里放一个同名元素，它就挂进来。

**组件库内部新建的元素**：渲染以后补属性（`patchAfterRender`、`useLayoutEffect`）只在套件自己重新渲染时生效；组件库自己新建的元素（悬停才出现的弹层里的项）要直接给属性、或者等它出现再补。改属性用 MutationObserver 时只写不一样的值，写相同的值也会再触发它自己，页面卡死（Element 碰到过）。

**组件库的子元素完全不收属性**时（Arco 表头的勾选格、Element 勾选框的名字落在外层 label 上），可以接受的手段：组件库给的渲染钩子里 `cloneElement`（Arco 的 `components.header.operations`）、渲染后直接给 DOM 元素补属性（只在对齐档，见上一条）。

**按名字全局替换图标会波及别的组件**（TDesign 的 `globalConfig.icon` 换了分页的箭头，面包屑、下拉也在用同一个图标）：只在这个控件外面局部套一层；有的组件只在创建时读一次配置，换图标集时要给它一个 `key` 让它重建。

**受控也有例外**：Arco 的表格在所有列都没排序时把 `sortOrder` 为空当成「不受控」，点一下会先自己记一份。页面接受这次改动时结果一样；套件要保证「页面不接受」时也能拉回来（下一次渲染用页面给的值）。

**组件库自带的快捷键和接口约定冲突**时（TDesign 表格聚焦后按 Esc 清空全部勾选，连别的页的也清掉），按接口约定：对齐档关掉；原生档如实保留、记进适配记录。

**「打开时做一次」的事不要写在 ref 回调里**（React）：每次渲染都新建的 ref 回调，React 每次渲染都会重新调用。对话框「打开时把焦点放进第一个框」写成这样，表单里打一个字、页面重渲染，焦点就被拉回第一个框（antd、Arco 踩过，第二个字跑进了别的框）。用 `react/src/kit/useFocusOnOpen.ts`。检查里一次插入一整个词只渲染一次，抓不到；要逐字打（`keys` 里一个字一个 `{ text }`，`gap` 给 150）。

**Vue 的插槽**：模板里的注释在插槽里也是一个节点。组件库只取默认插槽第一个节点当触发按钮的（TDesign 的 Dropdown），注释会让按钮整个不见，要过滤掉。

### 4.4 写适配记录

每处「组件库默认和控件规格不一样」写一条，放在套件的 `adaptations` 里：

```ts
adapt('switch', 'size', ['默认 44×22', 'Default 44×22'], ['统一成 40×22', 'Unified 40×22'], 'component-token')
```

五个参数：哪个控件、哪方面（尺寸 / 颜色 / 形状 / 字 / 图标 / 状态 / 键盘 / 无障碍）、组件库默认怎么样、对齐成什么样、用的什么手段。键盘（`keyboard`）记「支持键盘但做法不一样」，无障碍（`a11y`）记「读屏、只用键盘的人用不了」：没有角色、Tab 进不去、读不到名字、aria 落错元素。组件库档案的 `accessibility` 一栏写这个组件库整体的无障碍情况。
**如果某个组件库「只设主题」就已经一致，一条都不用写**——这本身就是一个结论，写进发现清单。

### 4.5 测试里的朴素套件也补一个

`examples/src/structure.test.tsx` 里有两个「朴素套件」（React、Vue 各一个，只输出普通 HTML），用来核对两个框架的视图结构一样。给它们补一个最简单的实现和部件地图。

**做完的标志**：`npm run typecheck` 通过。

**截图看一眼**：有的问题检查量不到，截图才看得出来——聚焦外圈被外层的 `overflow: hidden` 裁掉、页面样式依赖的 `aria-expanded` 没有、悬停时多出来的提示。检查页加 `&mode=native` 是组件库原生，写适配记录要的「原生实测数字」也从这里量。

## 第 5 步：放进控件样张

**改哪里**：`examples/src/scenes/controls/` 下的四个文件

1. `state.ts`：加上这个控件要用的状态（比如 `enabled: true`）。
2. `ControlsView.tsx`（React）和 `ControlsViewVue.ts`（Vue）：各加一行，**结构完全一样**。外面包一层 `<div data-region="…">`，检查工具按区域量。把这个控件的各种状态都摆出来（开 / 关、禁用的开 / 关……）。
3. `index.tsx` 的 `checksFor`：加上这个控件要核对的交互，从这几种里选：
   - `focus`：键盘聚焦以后的边线和外圈；
   - `hover`：鼠标悬停以后的颜色；
   - `click`：真实点击以后，状态对不对；
   - `keys`：聚焦以后按键（空格、回车、方向键、Esc），状态和焦点对不对；
   - `popup`：点击打开弹层，量弹层和里面的项，Esc 收起；鼠标悬停才打开的（侧栏收起后的子菜单）写 `open: 'hover'`，移开鼠标收起；
   - `tabOrder` 已经有了，会自动把新控件算进去。

**页面里有对话框这类模态弹层**：检查页上几个组件库并排，几个模态对话框同时开着，每个都把焦点锁在自己里面、把页面别处设成不能点（Radix 给 body 加 `pointer-events: none`），点一下就互相抢焦点，浏览器会卡死。真实页面里只有一个。所以场景要提供 `solo(kit)`：「下次复原时只打开这个组件库的对话框」；检查工具和某个组件库交互（点击、按键、弹层、聚焦、Tab 顺序）之前会调用它、复原，再把别的格子设成 `inert`；「样子」也一个组件库一个组件库地量。客户列表场景（`examples/src/scenes/customers/`）是例子。

页面场景里的新控件也一样：在场景的 `checksFor` 里加检查项，目标用部件（`{ part: 'breadcrumbLink' }`）或页面结构（`'[data-region=sider] [role=menuitem]'`，第几个）找。

## 第 6 步：跑检查，修到全部通过

```bash
npm run audit:kits -- --scene=controls
```

先只跑控件样张（或新控件所在的场景），快；还可以只比两个库（`--kits=shadcn,antd`）、只跑一种组合（`--spec=mono --sider=expanded`）。报告会指到**哪个区域、哪个部件、哪一项、每个组件库各是多少**，比如：

```
✗ 样子 控件样张 · mono（2 处不一样）
    区域 › switch › switch[0] › 宽: {"antd":44,"element":40,"shadcn":32,"arco":40}
```

按报告回到第 4 步改，直到全过。

**常见的「量法」现象**（不是套件的问题，先认出来）：
- 文字、图标在半像素上，各组件库取整方向不同（antd 的弹层位置向下取整，Radix 四舍五入）——先看是不是布局把东西放在了半像素上；
- 过渡进行中颜色是 `rgba(…, 1)`、结束是 `rgb(…)`（检查已经算它们一样）；
- 0.5px 的上下差让文字排序翻过来，一处变成几十处（检查已经改成文字、图标先按内容再按位置排）。

**如果报告里的「不一样」眼睛看不出来**：先在浏览器里量一下，确认是不是**量法**的问题。比如「完全圆」的圆角，antd 写 100px、Element 写 11px、shadcn 写 9999px、Arco 写 50%，看起来一样，字符串不一样——这时改的是检查工具的量法（圆角按看得见的算），而且必须是对所有组件库都成立的通用规则，**不能为某个组件库开特例**，也不能为了通过去改套件。

几个人（或 AI 会话）同时做不同组件库时，**谁都别改共用的检查工具**：发现量法问题就把证据（报告里的哪一项、两边各是多少、页面里实测是什么）报告给负责共用文件的人，自己先做别的。可以在被忽略的 `output/` 里写一个改了量法的副本验证一下猜想，但不提交。

报告最后一行写着「几项里几项不一样，一共多少处」——「接上、还没对齐」时的这个数就是第一次检查的数字。

**组件库的语言包**：接中文页面时把组件库的语言包配上（antd 的 `ConfigProvider locale`、Element 的 `ElConfigProvider`……）。日期面板的月份星期、分页的「共 N 条」、读屏名字（「Select this row」「上一页」）都跟语言包走，配不配会直接改变「原生实测」的数字。

**组件库收起弹层时让控件失去焦点**（Arco 的日期框、选择框一收起焦点就掉到 body）、**不管什么情况都拦下 Esc**（Arco、Element 的选择框收着时也 `stopPropagation`，对话框收不到第二次 Esc）：检查报焦点掉到 body、Esc 关不掉对话框时，先去组件库源码里找它在哪儿失焦、在哪儿拦 Esc。

**组件库的开关状态不受控**时（TDesign 的日期面板开没开是它自己存的）：可以模拟它认的操作（回车时点一下框，Esc 时往页面发一个「点在外面」），状态从它的事件里跟着记。

**为新控件改了已有的控件**（TDesign 为了对话框里的选择框，补了「回车、空格打开」）：会影响别的场景，跑全部场景；回头改旧的适配记录和档案（原来写的「回车本来就能用」可能不准）。

**写适配记录要的原生实测数字**：`npm run audit:kits -- --scene=<场景> --kits=<这个库> --mode=native` 只量不比，`output/audit/report.json` 里每一项的 `values` 就是组件库原生的样子。注意数字受页面内容影响（比如表格的行高会被格子里 32 高的按钮撑开），写记录时说清楚是在什么内容下量的。

**几个人（或 AI 会话）同时做时的环境**：每人用自己的端口起开发服务器（`npx vite --port <自己的端口>`，不要用 `npm run dev` 固定的 4182）；不要用几个会话共用的浏览器面板，用 `audit/lib/chrome.mjs` 起自己的无头 Chrome 量和截图；标签页在后台时组件库的进场动画会停在第一帧，截图前先放到前台或等动画。

**确认检查真的按到了目标**：按键检查先聚焦目标再按键；目标如果是不能聚焦的外框（antd 的选择框部件是外框 div），焦点其实在 body 上，按 Esc 会关掉整个对话框，看起来像组件库的 bug。键盘目标用角色找（`[role=combobox]`），不要用部件。

全过以后跑完整的：

```bash
npm run check
```

**做完的标志**：`npm run check` 全部通过。
